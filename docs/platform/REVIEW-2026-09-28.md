# Pleadli: review, research and plan (DPP, Police, Prisons)

Written 2026-09-28 after the client's feedback. Nothing in this document has been built. It is the audit, the research, the suggestions and a staged plan, and it ends with the decisions that need approval before any code.

Order of concern, as asked: **DPP first (the concentration), then Police, then Prisons.**

## 0. The client's feedback, in one list

1. The structure still looks tacky and does not show how cases are really organised.
2. The reference numbers each country uses (CRB, OB, RB, Js...) must be first class.
3. AI support that simplifies the work: summarise everything, reference the country's own laws, give the prosecutor the best options and reasons, turn the work into simple tasks.
4. Task board, workflow, timeline, kanban.
5. Filings, statistics.
6. Documents that look and print like the real legal document (Word feel, letterhead, signature, stamp).
7. Two kinds of API: one that lets a government plug in its own systems and sync (often AWS, with its own encryption), one that lets granted apps on the network search cases.
8. A clear split between facility (station, office, prison) and headquarters, in setup and in settings.
9. A smooth first launch: loading, introduction, licence, jurisdiction, country, language, model (facility or HQ), protection level, first users, own colours and logo.
10. It feels laggy.
11. Police: dispatch as an Android app, real calling, tracking, search; a plugin structure for national ID, fingerprint, face, social media (with permission).
12. French, and language that switches everywhere in real time.
13. An Apple-like premium feel. Today it is "not bad, just not well thought, and too techy for a DPP who is not a tech person".

## 1. Audit: what exists today

### DPP (`apps/dpp`)

Built (per `docs/dpp/PLAN.md`, Stages 0 to 8): charging review with the real Two-Stage and Threshold tests, per-count decisions, append-only decisions with reopen/correct, structured directions on a return to Police, a document library (charge sheet, directions to Police, reasons for declining) with DOCX export and print, capacity charts, SQLCipher encryption, app lock, backups, hash-chained audit, and the DPP side of a signed Police to DPP package exchange. About 11,600 lines of TypeScript, 8,000 of Rust, 971 strings in en/sw/de.

What is right and should be kept: the legal core. Decisions cannot be silently edited, status is derived, discontinue and nolle prosequi are refused unless the user is the DPP, a return must carry directions. This is the hard part and it is sound.

What is wrong (the client's "tacky, unstructured, too techy"):

| Finding | Evidence |
|---|---|
| 18 navigation entries for one prosecutor. Five of them are the same list (Intake, Active, Returned, Reopened, Closed) and four duplicate what already lives inside a file (Police material, Decisions, Documents, Court). | `apps/dpp/src/data/navigationItems.ts` |
| The file is organised by software concepts (Chronology, Review, Decisions), not by the parts of a real prosecution file. There is no cover, no index, no sub-file order, no page/sheet numbering. | `features/file-workspace/workspace.tsx` |
| Reference numbers are text fields, not the file's identity. The ODPP number is free text; the court number is not a badge on the file. | `PRODUCT.md` §1 |
| Technical words in the prosecutor's face: "SHA-256 of the package", "Encrypted with SQLCipher", "Key in the system keystore", "Key fingerprint", "Import a package", "replayed from each file's referrals". 31 such strings. | `apps/dpp/messages/en.json` |
| No tasks, no board, no calendar, no hearing diary. Work queues exist only as filtered lists. | nav + routes |
| Documents render as blocks (heading/paragraph/fields), not as a page with letterhead, margins, signature and stamp. Editing is not Word-like. | `domain/document_content.rs`, `features/documents/` |
| No first-run setup at all. DPP starts straight into the workspace with a profile form in Settings. | no onboarding feature in `apps/dpp/src` |
| "One prosecutor per installation" (a 2026-09-11 decision) conflicts with the new request for HQ vs facility and "create first users". | `PRODUCT.md` §Organizational responsibility |
| Language: 7 routes still hardcoded English (files, search, material, decisions, court matters, documents, reports); dates are English everywhere (date-fns without locale, 23 files); server error messages and generated documents are English only; no French. | scan of `apps/dpp/src` |

### Police (`apps/police`)

Built: station workspace (front desk, custody, investigations, station, administration), SD and CRB numbering (`{station} CRB n/year`), custody deadline board, one officer record, units tree, station vs command (HQ) installation, badge sign-in, encrypted DB, backup-assistance flow with phone pairing over Cloudflare Tunnel. 20,000 lines TS, 13,400 Rust, fully translated en/sw/de.

Gaps against the new brief: no mobile app (dispatch is a desktop page plus a phone web page through the tunnel), no calling, no GPS tracking, no plugin structure, the Police side of the DPP package exchange is not built (a referral is still a local record), the file has no sub-file structure either.

### Prisons (`apps/prisons`)

The most mature shell: five-screen facility setup, HQ onboarding, facility-first model, sign-in policies (password, PIN, badge only), inbox, sync seam to Head Office, issued documents with verification, full string extraction (about 2,350 messages), jurisdiction pack seam (`ug` only). 29,000 lines TS, 23,700 Rust.

Gaps: its setup order is not the one the client asked for (no licence, no protection level choice, no branding step), jurisdiction packs other than Uganda are research pages only, the facility/HQ settings split exists but "Set by Head Office" chips are unused, AI is a documented seam with nothing built, not yet seen in the real Tauri window.

### Across all three

- Three different first-run experiences (none, installation choice, five-screen setup). The client wants one.
- Logo is per computer (localStorage), not per institution, so a second machine shows the default crest. No colour branding.
- Every app repeats the same shell, i18n, brand, security, query client code. A shared setup/brand/jurisdiction package would stop the drift.

## 3. Research: how case files are organised and numbered

Confidence labels: **P** primary or official source read, **S** secondary (named source, search result, practitioner material), **U** unknown, not found. Earlier repo research (`docs/police/research/`, `docs/dpp/research/`, `docs/prisons/jurisdictions/`) is reused, not repeated.

### Reference numbers per country

| Country | Police reference | Prosecution reference | Court reference | National systems |
|---|---|---|---|---|
| **Uganda** | SD (Station Diary) entry when reported; case file number `{STATION} CRB {n}/{year}` e.g. "JINJA CRB 314/2019" (S, three High Court citations). Every sheet in the file carries "Case File No." and "Sheet No." by hand (P, Police Forms 2A/2B). | ODPP registration number, format not published (U). Separate number per unrelated charge (P, Decision to Charge Guidelines 2023). | High Court: `HCT-{code}-CR-SC-{seq}-{year}` (S). Magistrates: "Criminal Case No. n of year" (S). | Police ePIS; ODPP **PROCAMIS** (electronic registry, document imaging, referral point); Judiciary **ECCMIS**; integration through **UGhub** (NITA-U, WSO2 based, 150+ entities incl. NIRA, Police, Judiciary) (S). |
| **Kenya** | **OB** (Occurrence Book) number `OB {n}/{day}/{month}/{year}` e.g. "OB 8/10/03/2023"; police case number `CR {n}/{year}` (S, charge sheet "Police 5" form). An OB only proves a report was made. | ODPP number on the charge sheet ("ODPP MSN No.") (S). ODPP system **Uadilifu**, integrated with Judiciary e-filing (S). | "Criminal Case No. E{n} of {year}" since e-filing (S, needs confirming). | Digital OB rollout; Judiciary e-filing and case tracking. |
| **Tanzania** | **RB** (Report Book, Police Form 162) number when reported (S); IR (investigation register) not confirmed (U). | NPS reference (U). | Judiciary **JoT-eCMS** since Nov 2023, reads NPS and NIDA systems (S). | e-CMS; NIDA. |

| **Burundi, South Sudan, DRC, Somalia** | Not researched in this pass (U). Backlog, not out of scope. | | | |
| **Germany** | Police **Vorgangsnummer / Tagebuchnummer** per report (S). | Staatsanwaltschaft **Aktenzeichen** `{Dezernat} Js {n}/{yy}` e.g. "12 Js 1234/15"; variants JuJs (juvenile), KapJs (capital) (S, federal register signs list). | Court Aktenzeichen with its own register sign (e.g. Ds, Ls, KLs) (S). | Electronic file mandatory in criminal cases from 1 Jan 2026, states may defer to 2027 (S). | **France** | Police/gendarmerie **numéro de procédure** + unit code + PV (procès-verbal) numbers (S). | **Numéro de parquet (NPP)**, given when the prosecutor registers the case, follows it to court (S). Courts system **Cassiopée**. | Same NPP carried. | **PPN** (procédure pénale numérique): fully digital files with electronic signatures, 9.3M procedures, 57% of tribunals fully deployed end 2025 (S). |

### How the file itself is organised

- **Kenya (S, several practitioner sources):** a lettered file. A initial/incident reports, B documentary evidence, C expert reports, D witness and suspect statements, E accused's statements (E1, E2...), F investigation diary (F1, F2...), G charge sheets, H lists of witnesses, exhibits, prisoner property, criminal record, I the investigating officer's covering report, J minute sheet.
- **Uganda (U):** no published order was found. Uganda shares the same colonial police-order heritage, and the Kenya structure is a plausible starting template, but it must be confirmed by a Ugandan prosecutor or officer before it is shipped as "Uganda". Known for sure: sheet-numbered pages, "Case File No." on every sheet.
- **Germany (S):** one continuous file, pages numbered (Blatt), with separate Beiakten and Sonderhefte (exhibit and special volumes).
- **France (S):** the procédure is a sequence of numbered PVs (each act is its own record), transmitted as one signed digital bundle under PPN.

**What this means for Pleadli:** the file structure, the numbering formats and the document templates are **jurisdiction-pack data**, not code. A Kenyan install shows sub-files A to J and OB/CR numbers; a Ugandan one shows CRB and sheet numbers; a German one shows Js and Blatt. The core file workspace is the same.

## 4. Research: how governments frame AI in justice

| Source | What it says |
|---|---|
| **Uganda Judiciary**, Judges' Annual Retreat, Kampala, 2 to 4 Feb 2026 (paper by Justice Isaac Lenaola, Supreme Court of Kenya) (P) | AI as a "supportive, non-decisional tool", to "augment efficiency in the organisation, structuring, summarisation and retrieval of information, particularly in complex matters with voluminous records". Warns about hallucinated cases and citations; requires human oversight and independent verification. |
| **Kenya Judiciary** AI Adoption Policy Framework, draft in public participation (S) | Human in the loop; AI output is "informational" and must be verified by a human before official use; uses: research, case management, scheduling, transcription. |
| **EU AI Act** Annex III (S) | AI that assists judicial authorities in researching and interpreting facts and law, and many law-enforcement uses, are **high risk**: risk management, logging, transparency, human oversight. Deadline moved to 2 Dec 2027. Applies to Germany and France deployments. |
| **Germany** (S) | Narrow assistants for mass cases (OLGA in Stuttgart, FRAUKE in Frankfurt) that extract and structure, never decide. |
| **France** (S) | Focus is the digital file (PPN) and signed data first, analytics after. |
| **Data protection** (S) | Uganda DPPA 2019 s.19: personal data processed outside Uganda only where protection is equivalent or the person consented. Kenya Data Protection (General) Regulations 2021 reg. 26: some state-interest processing must be on a server in Kenya or keep a copy there. |

**The consistent line:** AI summarises, structures, retrieves and drafts; a named human decides and signs; every AI output is labelled, cited, logged, and verifiable; data stays where the law says. Pleadli's existing AI stance (`docs/prisons/AI.md`) already matches this and becomes the platform rule.

## 5. Suggestions

### 5.1 The DPP, redesigned around the real file

**Navigation, from 18 entries to 7:**

```
Today        what needs me now: deadlines, hearings, new files, tasks
Files        every file, with saved views (New, In review, With Police, In court, Closed)
Board        tasks as kanban (To do, Doing, Waiting on Police, Waiting on court, Done)
Calendar     hearings, Threshold reviews, trial-date notices, returns due
Documents    everything drafted, awaiting signature, signed, filed
Statistics   received, decided, returned, in court, turnaround (work, never people)
Search
             Settings (bottom)
```

Police material, decisions, court and documents stop being top-level pages; they live inside the file, where a prosecutor expects them.

**The file workspace looks like the file:**

- A **cover**: the three reference numbers as badges (Police `KIRA ROAD CRB 221/2026`, DPP ref, court ref), accused, offence, stage, assigned prosecutor, next date.
- An **index** on the left in the jurisdiction's order (Kenya A to J; Uganda once confirmed), each document with its sheet numbers, like tabs in a real folder.
- A **timeline** across the top: reported, referred, reviewed, decided, charged, first hearing, adjournments, judgment.
- A **"Next step" card** in plain words: "Decide whether to charge. 4 statements, 2 exhibits received. Evidence test not started."
- **Assist panel** on the right (see 5.3).

**Plain language everywhere.** "SHA-256 of the package" becomes "Checked: not altered since the station sent it". "Import a package" becomes "Receive a file from a police station". Security wording moves to one "Protection" card that says "Your files are locked on this computer." Technical detail stays one click away for IT staff.

**Filings:** a filing register per file (what was filed, in which court, when, receipt/stamp), feeding the Calendar and the court badge.

### 5.2 Documents that look legal

- A **page view** (A4, margins, letterhead with the institution's crest and address, running header with the file references, page numbers "Page 2 of 5", sheet numbers).
- **Word-like editing** on the page itself (headings, numbered paragraphs, counts, tables), with templates per jurisdiction pack (charge sheet, indictment, summary of the case, directions to Police, reasons for declining, legal opinion).
- **Signature and stamp:** a stamp image and a signature image per authorised officer, placed on the page; plus a digital signature and a QR code that a court or station can scan to verify the document was issued and not altered (Prisons already has issue-and-verify).
- **Output:** print, PDF, DOCX that opens in Word identical to the screen.

### 5.3 AI Assist (DPP first)

What it does, in the order a prosecutor needs it:

1. **Summarise the file**: facts, people, what each statement says, contradictions, what is missing against the evidence list the Decision to Charge Guidelines require.
2. **Reference the law**: offences and sections that fit the facts, with the text quoted from the **jurisdiction's law library** (Penal Code, Magistrates Courts Act, Trial on Indictments Act, Guidelines), never from model memory. No citation without a link to the source text.
3. **Options for the decision**: charge / return with directions / decline / divert / Threshold, each with reasons against the named Evidential and Public Interest criteria, and a recommended option. The prosecutor decides; the decision record says who decided and whether Assist was used.
4. **Turn it into tasks**: "Request the medical report (PF3)", "Record statement of the second witness", which drop onto the Board and, if returned, into the directions letter to Police.
5. **Draft documents** from the file into the page editor, marked as draft until signed.

How it is run (the government chooses, off by default):

| Mode | Where the model runs | Fits |
|---|---|---|
| Off | nowhere | default |
| On this computer | a local model | no data leaves the office |
| Government cloud | the government's own account (for example AWS Bedrock in their region, with their own KMS keys) | ministries on AWS; data residency |
| Institution key | a provider key the institution supplies | pilots |

Every AI action is logged (who, what file, what was produced), and outputs carry an "AI draft, not verified" label until a person accepts them. This matches the Uganda and Kenya judiciary lines and the EU high-risk duties.

### 5.4 First launch, the same in every app

```
1 Loading          crest, name, progress
2 Introduction     three short screens: what this app does, what it never does, how data is protected
3 Licence          full text to read, accept to continue (public, readable before setup)
4 Where            jurisdiction/country -> language (defaults from country, changeable)
5 Model            Facility (station / office / prison) or Headquarters, only where that institution has an HQ;
                   a facility can connect to its HQ now or later
6 Protection       None / Basic / Full (below)
7 Look             institution name, logo, colours (preview live on the next screens)
8 First people     administrator first, then optional others
9 Done             a short tour of Today
```

Protection levels (proposal, decision D5):

| Level | Sign-in | Data |
|---|---|---|
| None | no sign-in, one person on a trusted machine | still encrypted on disk (it already is), backups optional |
| Basic | each person has a PIN or password, app locks when idle | encrypted, backups on |
| Full | password + second factor, admin approval for new users, all actions audited, backups mandatory and encrypted | encrypted, key recovery set up |

"Start from clean setup" means: when this ships, existing test data is backed up and the apps start from this flow on an empty data folder.

Logo and colours are stored **with the institution** (in the database and sent to connected facilities), not in the browser, so every computer shows the same crest.

### 5.5 Facility and headquarters, clearly separated

- Setup asks once. The app's header shows which one it is (for example "Wandegeya DPP Office" vs "ODPP Headquarters").
- Settings has two groups: **This office** (things the office controls) and **Set by headquarters** (read-only here, with a small "HQ" chip). HQ has an extra **Facilities** section: approve connections, push policies, see returns.
- Applies to Police (station / command), DPP (station or regional office / headquarters, which needs D1), Prisons (unit / HQ, already close).

### 5.6 Two APIs, and plugins

**A. Government integration (sync).** For a ministry that wants its own systems to receive or send data.
- Standard REST + webhooks with a published OpenAPI description; events like `file.referred`, `decision.recorded`, `document.issued`.
- Authentication by client certificates (mutual TLS) or OAuth client credentials; every payload signed, and optionally encrypted with the **government's own key** (AWS KMS or their HSM).
- Adapters: **UGhub** (Uganda's government integration bus, WSO2 based, already connects Police, Judiciary, NIRA), **AWS** (S3 + EventBridge or API Gateway in their account and region), a generic HTTPS target. Choosing an adapter is a settings card, not code.
- The existing signed package format (`packages/interchange`) is reused as the payload envelope, so offline (file) and online (API) carry the same thing.

**B. Network search (granted access).** For another app on the justice network to ask "does this case exist, what stage is it at".
- Nothing is visible by default. HQ grants a named app a scope (for example "Courts may look up a DPP file by police reference, see stage and next date"), with an expiry.
- Every lookup is logged and visible to the owning office.
- "Referenceability is not visibility" stays the rule.

**Plugins (Police first, same structure everywhere).** A plugin is a signed package that declares what it needs (read person, call external service) and does nothing until HQ enables it and the legal basis is recorded. Candidates: national ID check (NIRA via UGhub; Kenya IPRS; Tanzania NIDA), fingerprint (AFIS), face match, social media search. Face and social media search carry the highest rights risk and, in the EU, real-time remote face identification in public is mostly prohibited; they ship disabled with a clear warning and per-use justification.

### 5.7 Police mobile dispatch

- A **Tauri Android app** for officers in the field (same codebase family, Tauri v2 supports Android): receive dispatch, accept, navigate, update status, call.
- **Tracking:** the phone reports location while on duty only, shown on the station's dispatch map; history kept per shift.
- **Calling:** in-app voice between station and officer over the station's own connection (WebRTC), with a normal phone call as fallback. Which carrier or voice provider is used is an open question (D9).
- **Search** from the phone: person, vehicle, case by reference, subject to the same permissions.
- The desktop station stays the hub; the phone pairs with it using the existing pairing QR.

### 5.8 Language

- Add **French** to all apps (Prisons already has an empty `fr.json`), full catalogs, not scaffolds.
- **Real-time switch everywhere**: the floating selector and the Settings selector call the same function; screens re-render without remounting; dates and numbers use the language (`Intl`), not English date formats; server messages are sent as codes and translated in the app; documents can be generated in the chosen language where the jurisdiction allows.
- Finish the 7 DPP pages still in English.

### 5.9 The premium feel

Concrete rules, not adjectives: one typeface scale and generous spacing; fewer borders, more grouping by space; one accent colour per institution (from setup); sheets and panels that slide, 150 to 250 ms, reduced-motion respected; every empty state says what to do next in one sentence; plain-language labels; keyboard first (command menu, shortcuts shown in menus); nothing technical on the first screen of anything.

## 7. Decisions needed before any code

| # | Decision | Recommendation |
|---|---|---|
| D1 | DPP was defined as "one prosecutor per installation". The new setup (HQ vs facility, first users) implies a regional office with several staff and an HQ. Reverse it? | Yes: a DPP station/office has several users; HQ is a separate install that sees its offices. |
| D2 | Which countries get a full pack first? | Uganda complete, Kenya second (best documented file structure), Tanzania and Rwanda after. Germany and France as language plus reference formats only until there is a customer. |
| D3 | Use the Kenya A to J file order as a provisional Uganda layout until a Ugandan practitioner confirms? | Yes, labelled "provisional" in the pack, changeable per office. |
| D4 | One shared setup package for all apps, or copy the flow per app? | Shared package. |
| D5 | Protection levels as in 5.4, and "None" still encrypts the disk? | Yes. |
| D6 | Branding: logo + one accent colour, or a full colour theme? | Logo + accent colour + optional letterhead; full themes invite unreadable results. |
| D7 | AI: which run modes to build first, and who pays for model usage? | Off + government cloud (AWS Bedrock in their account) + institution key; local model later. |
| D8 | Integration: first adapter? | UGhub (Uganda's own bus) and AWS; generic HTTPS comes free. |
| D9 | Calling: in-app voice over the station's connection, a telecom voice provider, or plain phone calls? | In-app voice with phone-call fallback; confirm with the client which carrier/provider governments allow. |
| D10 | Plugins allowed in the first release: national ID only, or also fingerprint, face, social media? | National ID first; the others as disabled plugins requiring HQ approval and a recorded legal basis. |
| D11 | "Start from clean setup": wipe the current test data on the next release (after an automatic backup)? | Yes. |

Nothing will be coded until these are answered or the recommendations are accepted.
